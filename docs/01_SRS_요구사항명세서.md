# 1. 서론

## 1.1 목적

파이썬 프로젝트의 의존성을 분석해 **라이선스 판정**과 **알려진 취약점**을 제시하는 웹 애플리케이션의 요구사항을 정의함.

| 독자 | 이 문서에서 얻을 것 |
|---|---|
| 개발팀 6인 | 구현할 기능과 완료 기준 |
| 담당 교수 | 요구사항의 근거와 검증 방법 |

## 1.2 제품 범위

### 하는 일

- `requirements.txt` 또는 `pip freeze` 출력을 입력받음
- 전이 의존성까지 전개함
- 각 패키지의 라이선스를 식별하고, 사용자가 고른 프로젝트 라이선스 기준으로 판정함
- 버전이 확정된 패키지의 알려진 취약점을 조회함
- 결과를 위험 순으로 보여줌

### 하지 않는 일

| 제외 | 이유 |
|---|---|
| 파이썬 외 생태계 (npm, Maven 등) | 학기 범위 초과 |
| 소스 파일 내용 스캔 | 메타데이터 신뢰 방식과 전제가 다름 |
| 정적·동적 링크 등 결합 형태 판정 | 법률 판단 영역 |
| 라이선스 변경 제안 | 법적 위험 |
| 사용자 계정·이력 저장 | 무상태 도구로 충분 |
| 표준 SBOM 출력 | 확장 방향으로만 남김 |

### 목표

| ID | 목표 | 관련 요구사항 |
|---|---|---|
| G1 | 사용자가 실제로 설치되는 패키지 규모를 앎 | FR-DEP-*, FR-OUT-01 |
| G2 | 배포 전에 알아야 할 위험을 놓치지 않음 | FR-JDG-*, QR-A-04 |
| G3 | 사용자가 판정 근거를 스스로 확인할 수 있음 | FR-LIC-10, FR-JDG-10 |
| G4 | 설치 없이 브라우저만으로 사용함 | FR-IN-01, DC-04 |

## 1.3 용어

| 용어 | 정의 |
|---|---|
| 직접 의존성 | 사용자가 입력 파일에 직접 적은 패키지 |
| 전이 의존성 | 직접 의존성이 필요로 해서 함께 설치되는 패키지. 화면에서는 「따라온 패키지」로 표기 |
| extras | `pkg[extra]` 형태로 요청하는 선택적 의존성 묶음 |
| SPDX 식별자 | 라이선스의 표준 이름. 예: `MIT`, `Apache-2.0` |
| SPDX 표현식 | 식별자를 `AND`·`OR`·`WITH`·괄호로 조합한 문자열 |
| 공개조건 | 배포 시 소스 공개를 요구하는 라이선스 조건 (카피레프트). 화면에서는 「조건」으로 표기 |
| 등급 | 공개조건의 강도. 0(조건 없음)~4(네트워크 제공도 공개) — 부록 A |
| 신뢰 수준 | 라이선스 식별 결과의 확실성. 확실 / 추정 / 미상 |
| 판정 | 프로젝트 라이선스 기준 사용 가능 여부. 안 됨 / 모름 / 조건 있음 / 판단보류 / 써도 됨 |
| 확정 버전 | 실제 설치될 버전이 정해진 상태. `이름==버전` 입력에서만 얻음 |

## 1.5 표기 규칙

### 요구사항 문장

EARS 형식을 한국어로 옮겨 씀. 한 요구사항에는 「해야 함」을 하나만 둠.

| 유형 | 형식 |
|---|---|
| 상시 | 시스템은 ~해야 함 |
| 사건 | ~하면, 시스템은 ~해야 함 |
| 비정상 | ~인 경우, 시스템은 ~해야 함 |
| 선택 | ~ 기능이 포함된 경우, 시스템은 ~해야 함 |

### ID 체계

| 접두 | 범주 |
|---|---|
| `FR-IN` | 입력 |
| `FR-DEP` | 의존성 전개 |
| `FR-LIC` | 라이선스 식별 |
| `FR-JDG` | 판정 |
| `FR-VUL` | 취약점 |
| `FR-OUT` | 결과 제시 |
| `IF-UI` / `IF-SW` | 사용자 / 소프트웨어 인터페이스 |
| `QR-P` / `QR-R` / `QR-A` / `QR-U` / `QR-S` | 성능 / 신뢰성 / 정확성 / 사용성 / 보안 |
| `CR` | 준수 |
| `DC` | 설계·구현 제약 |
| `DR` | 데이터 |

ID는 한번 붙이면 바꾸지 않음. 삭제한 요구사항은 번호를 재사용하지 않고 「삭제」로 남김.

### 우선순위

| 표기 | 뜻 | 인도 |
|---|---|---|
| M | 없으면 제품이 성립하지 않음 | **최소 완성본. 전부 구현해야 함** |
| S | 있어야 제대로지만 없어도 동작함 | M 완료 후 |
| C | 있으면 좋음 | 여유가 있을 때 |

### 검증 방법

| 기호 | 방법 |
|---|---|
| T | 시험 — 자동화 테스트 |
| D | 시연 — 실행해 보고 확인 |
| I | 검사 — 코드·화면·문서 검토 |
| A | 분석 — 측정·통계 |

# 2. 제품 개요

## 2.1 제품 조망

독립 실행형 웹 애플리케이션임. 외부 시스템 세 곳에서 정보를 받아옴.

```
             ┌──────────────────────────┐
  사용자 ───▶│   의존성 점검 웹앱        │───▶ PyPI     (패키지 정보·의존성)
 (브라우저    │                          │───▶ OSV      (취약점)
  또는 CLI)◀─│                          │◀─── SPDX 목록 (기동 시 1회)
             └──────────────────────────┘
```

내부 구성은 `02_설계지침.md`에서 다룸.

## 2.2 제품 기능

| ID | 기능 | 우선 | 관련 요구사항 |
|---|---|---|---|
| F1 | 의존성 목록 입력 | M | FR-IN-* |
| F2 | 전이 의존성 전개 | M | FR-DEP-* |
| F3 | 라이선스 식별 | M | FR-LIC-* |
| F4 | 프로젝트 라이선스 기준 판정 | M | FR-JDG-* |
| F5 | 결과 표시 (웹·CLI) | M | FR-OUT-*, IF-UI-* |
| F6 | 취약점 조회 | S | FR-VUL-* |
| F7 | 결과 내보내기 | S | FR-OUT-06 |

## 2.3 제품 제약

3.5절에 둠. 요지는 다음과 같음.

- 무료·무인증 외부 API만 씀
- 2026-12-14 최종 발표에서 시연 가능해야 함
- 구현에 과목 강의 요소를 반영해야 함

## 2.4 사용자 특성

| 구분 | 주 사용자 | 평가자 | 유지보수자 |
|---|---|---|---|
| 누구 | 컴퓨터공학과 학부생 | 담당 교수, 수강생 | 개발팀 6인 |
| 파이썬 수준 | 수업 수준 | 전문가 | 2학년 |
| 라이선스 지식 | **거의 없음** | 있음 | 개발 중 습득 |
| 사용 상황 | 과제 제출 전 | 중간·최종 발표 | 학기 중 |

주 사용자가 라이선스를 모른다는 전제에서 출발함. 따라서 화면에는 전문 용어 대신 1.3절의 화면 표기를 씀.

## 2.5 가정과 의존 관계

| ID | 가정 | 깨졌을 때 |
|---|---|---|
| AS-1 | PyPI JSON API가 현 스키마를 유지함 | 해석 기능 수정 필요 |
| AS-2 | OSV API가 무료·무인증을 유지함 | F6 제외 |
| AS-3 | 패키지가 신고한 라이선스가 사실임 | 본질적 한계. 화면 고지로 대응 (CR-01) |
| AS-4 | 사용자가 자기 프로젝트 라이선스를 앎 | 기본값 MIT 제공 (FR-IN-06) |
| AS-5 | 시연 장소에 인터넷이 있음 | 캐시된 결과로 시연 |

## 2.6 요구사항 배분

| 인도 단위 | 포함 | 완료 판정 |
|---|---|---|
| 최소 완성본 | 우선순위 M 전부 | 4.3절 인수 시나리오 AT-1 통과 |
| 확장본 | S 전부 | AT-2 통과 |
| 선택 | C | 개별 시연 |

요구사항별 담당 모듈은 설계지침 §8, 날짜는 수행계획서 §2에 있음.

## 3.1 외부 인터페이스

### 3.1.1 사용자 인터페이스

**입력 화면**

```
┌─────────────────────────────────────────────────┐
│  의존성 점검                                      │
│                                                 │
│  ① 의존성 파일   [ 파일 선택 ]  또는 붙여넣기        │
│  ② 내 프로젝트 라이선스   [ MIT ▾ ]                │
│  ③ [ 확인하기 ]                                   │
└─────────────────────────────────────────────────┘
```

**결과 화면** (웹앱 구성 11줄 입력 시의 실측 기준)

```
┌─────────────────────────────────────────────────┐
│  30개를 확인했습니다  (직접 11 · 따라온 19)         │
│  ─────────────────────────────────────────────  │
│  ● 조건 있음   certifi 2026.x   MPL-2.0          │
│     └ 이 패키지를 고쳐 썼다면 고친 부분만 공개       │
│  ─────────────────────────────────────────────  │
│  ✓ 나머지 29개는 문제 없습니다        [ 펼치기 ]    │
│  ─────────────────────────────────────────────  │
│  출처: SPDX · PyPI · OSV                          │
│  이 결과는 법적 조언이 아닙니다.                    │
└─────────────────────────────────────────────────┘
```

| ID | 요구사항 | 우선 | 검증 |

| IF-UI-01 | 입력 화면은 파일 선택, 붙여넣기, 라이선스 선택, 실행 버튼으로 구성되어야 함 | M | I |

| IF-UI-03 | 화면 폭이 768px 이상인 경우, 시스템은 가로 스크롤 없이 결과를 표시해야 함 | S | D |
| IF-UI-04 | 시스템은 명령줄에서 `python -m oss_check <파일>` 형태로 같은 분석을 실행할 수 있어야 함 | M | T |

## 3.2 기능 요구사항

### 3.2.1 입력 — FR-IN

| ID | 요구사항 | 우선 | 검증 |
|---|---|---|---|
| FR-IN-01 | 사용자가 `requirements.txt` 파일을 올리면, 시스템은 그 내용을 분석 대상으로 받아야 함 | M | T |
| FR-IN-02 | 사용자가 의존성 목록을 텍스트로 붙여 넣으면, 시스템은 파일 입력과 같게 처리해야 함 | M | T |
| FR-IN-03 | 시스템은 주석(`#` 이후)과 빈 줄을 무시해야 함 | M | T |
| FR-IN-04 | 시스템은 PEP 508 표기(이름, extras, 버전 지정, 환경 마커)를 해석해야 함 | M | T |
| FR-IN-05 | 해석할 수 없는 줄(`-r`, `-e`, URL 등)인 경우, 시스템은 그 줄을 건너뛰고 줄 번호와 사유를 경고로 남겨야 함 | M | T |
| FR-IN-06 | 사용자가 프로젝트 라이선스를 고르지 않으면, 시스템은 MIT를 기준으로 써야 함 | M | T |
| FR-IN-07 | 입력이 `이름==버전` 형식인 경우, 시스템은 그 버전을 확정 버전으로 기록해야 함 | S | T |
| FR-IN-08 | 입력 크기가 1MB를 넘는 경우, 시스템은 분석하지 않고 크기 초과를 알려야 함 | M | T |

### 3.2.2 의존성 전개 — FR-DEP

```python
# 요구사항 개수 세기 — 저장소 scripts/count_reqs.py
import re, collections
s = open("docs/SRS.md", encoding="utf-8").read()
c = collections.Counter()
for rid, rest in re.findall(r"^\| ((?:IF|FR|QR|CR|DC|DR)-[A-Z0-9-]+) \|(.+)$", s, re.M):
    pr = next((x.strip() for x in rest.split("|") if x.strip() in "MSC" and x.strip()), None)
    if pr:
        c[(rid.split("-")[0], pr)] += 1
for k in sorted(c):
    print(*k, c[k])
```
