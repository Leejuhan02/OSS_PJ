## 0.1 가장 중요한 발견 — 그리고 그것이 뒤집힌 과정

> **이 절은 두 번 쓰였다.** 1차 측정 후 "충돌은 드물다"고 결론냈다가, 교차 검증에서
> **그 결론이 측정 설계의 결함에서 나온 것**임을 발견해 다시 썼다. 과정을 그대로 남긴다.

### 1차 결론 (틀림)

실제 프로젝트 5종(고유 144개 패키지)에 MIT 기준으로 판정을 돌렸더니 **「안 됨」이 0건**이었다. 여기서 "충돌 탐지라는 전제가 약하다"고 결론냈다.

### 왜 틀렸는가 — 두 가지 측정 결함

**결함 1. 해석기가 `extras` 의존성을 전부 버렸다.**

의존성 해석기가 `extra == "..."` 마커가 붙은 의존성을 건너뛰도록 짜여 있었다. 마커 제외 건수를 분해해보니 이렇다.

| 표본 | 제외 합계 | `extra` 마커 | 진짜 환경 마커 |
|---|---:|---:|---:|
| 데이터 분석 | 762 | **743 (98%)** | 19 |
| 웹앱 | 127 | 122 (96%) | 5 |
| Django | 105 | 100 (95%) | 5 |

**즉 extras 경로로 들어오는 의존성은 측정 설계상 관측될 수 없었다.** 「안 됨 0건」은 발견이 아니라 구조적으로 보장된 결과였다.

그리고 **반례가 표본 안에 있었다.** 데이터 분석 표본에 포함된 `jsonschema`를 직접 확인한 결과다.

```
jsonschema[format]         →  ... rfc3987        ← license: "GNU GPLv3+"
jsonschema[format-nongpl]  →  ... rfc3987-syntax ← license_expression: "MIT"
```

`format-nongpl`이라는 extra가 **존재한다는 사실 자체가** 파이썬 커뮤니티가 이 문제를 실재하는 것으로 다룬다는 증거다. GPL을 피하려고 대체 extra를 따로 만들어 둔 것이다.

**결함 2. 「미상」 통 안에 공개조건 패키지가 숨어 있었다.**

미상 188건을 분해했다.

| 분류 | 건수 | 비율 |
|---|---:|---:|
| 정말 아무 표기도 없음 | 101 | 3.37% |
| **표기는 있는데 우리 해석기가 변환 실패** | **87** | **2.90%** |

변환 실패 87건 중 **공개조건이 명백한 것이 24건**이었다.

```
pyqt5           GPL v3            pymupdf        AGPL 3.0
pyinstaller     GPLv2-or-later    pymupdfb       AGPL 3.0
fuzzywuzzy      GPLv2             pymssql        LGPL
unidecode       GPL               python-crontab LGPLv3
extract-msg     GPL               pyxlsb         LGPLv3+
pygit2          GPLv2 + 예외       func-timeout   LGPLv2
grandalf        GPLv2 | EPLv1     python-xlib    LGPLv2+
python-stdnum   LGPL              pyenchant      LGPL
gprof2dot       LGPL              cvss           LGPLv3+
formulas        EUPL 1.1+         schedula       EUPL 1.1+
browser-cookie3 lgpl              dynamodb-json  Mozilla
```

`pyqt5`(GUI), `pyinstaller`(배포 패키징), `pymupdf`(PDF, **AGPL**)는 학생 프로젝트에서 흔히 쓰는 것들이다.

### 2차 결론 (수정)

**충돌은 드물지만, 1차 측정이 보여준 것만큼 드물지 않다.** 그리고 **우리가 관측하지 못한 이유 자체가 도구가 필요한 이유다.**

| | 1차 결론 | 2차 결론 |
|---|---|---|
| 「안 됨」 0건의 의미 | 충돌이 드물다 | **해석기가 못 본 것이다** |
| 공개조건 비율 | 3.53% | **4.33%** (미상 속 24건 포함) |
| extras 경로 | 측정 안 됨 | **GPL 유입 경로로 실재 확인** |
| 위협 모델 | 무효 | **유효. 단 extras와 미상을 다뤄야 성립** |

**그러므로 요구사항이 바뀐다.** `extras` 처리(FR-C-09)와 별칭 사전 보강(FR-L-09, FR-L-13)은 「권장」이 아니라 **필수**다. 그것 없이는 도구가 자기가 잡아야 할 것을 못 본다.

### 그럼에도 가치 제안은 조정해야 한다

충돌이 실재하는 것과, 충돌이 **제품의 주된 가치**인 것은 다르다. 공개조건 4.33%는 여전히 소수이고, 취약점은 그보다 훨씬 흔하다(§3.3). 두 가지를 함께 놓는 것이 정직하다.

---

PyPI 상위 3,000개의 등급 분포는 이렇다. **아래 수치는 우리 해석기가 식별한 것만 센 것이므로, 공개조건 항목은 과소집계다**(위 결함 2).

```
허용형            2,634건  87.80%  ███████████████████████████████████████████
미상                188건   6.27%  ███
약한 공개조건          74건   2.47%  █
강한 공개조건(GPL)     31건   1.03%  ▌
독점                 27건   0.90%  ▌
등급 미등록           24건   0.80%  ▌
퍼블릭도메인           21건   0.70%  ▌
네트워크 공개(AGPL)     1건   0.03%
```

식별된 GPL 패키지는 31개(`ansible`, `pylint`, `mysqlclient`, `scapy`, `yamllint` 등), AGPL 1개다. 여기에 미상 속에 숨어 있던 24건을 더하면 **공개조건 패키지는 130개, 4.33%**가 된다.

이 중 상당수는 개발자가 직접 설치하는 **도구**(`ansible`, `pylint`)라서 배포물에 포함되지 않는다. 그러나 `pyqt5`, `pymupdf`, `mysqlclient`, `pyxlsb`처럼 **프로그램에 그대로 들어가는 라이브러리**도 적지 않고, `jsonschema[format]`처럼 **extras 경로로 딸려오는 것**도 실재한다.

## 0.2 실측으로 확인된 문제 — 중요도 순

**(1) 취약점은 흔하다. 그것도 압도적으로.**

같은 패키지 15개, 버전만 바꿔 OSV에 조회한 결과다.

| 표본 | 취약점 | 보유 패키지 |
|---|---:|---:|
| 2021년경 버전 고정 | **228건** | 12/15 |
| 2024년 말 버전 고정 | **130건** | 10/15 |
| 오늘 pip이 고른 버전 | **0건** | 0/15 |

학생 프로젝트는 `requirements.txt`에 버전을 고정해두고 학기 내내 갱신하지 않는다. 학기 초에 0건이던 것이 다음 학기 재사용 시점에는 수십 건이 된다. **라이선스 충돌보다 두 자릿수 이상 자주 발생한다.**

**(2) 라이선스를 못 읽는 경우가 6.27%다. 단, 그중 절반은 우리 잘못이다.**

| 분류 | 비율 | 의미 |
|---|---:|---|
| 정말 표기가 없음 | 3.37% | 저작권법상 **사용 허가가 없는 상태**. 진짜 경고 대상 |
| 표기는 있는데 변환 실패 | 2.90% | **우리가 고쳐야 할 것.** 여기에 공개조건 24건이 숨어 있었다 |

`mypy-extensions`(다운로드 129위), `azure-core`(173위), `azure-identity`(188위)는 전자에 가깝고(PyPI API 응답에 없음), `tiktoken`(149위)·`uritemplate`(230위)·`pymssql`(542위)은 후자다(표기는 있으나 형식이 비표준).

**두 경우의 대응이 다르다.** 전자는 사용자에게 경고할 것이고, 후자는 우리가 해석기를 고칠 것이다. 이 구분을 못 하면 자기 버그를 사용자에게 경고로 떠넘기게 된다.

**(3) 직접 적은 것과 실제 깔리는 것의 차이가 크다.**

| 표본 | 직접 | 전체 | 배수 |
|---|---:|---:|---:|
| 웹앱 구성 | 11 | 30 | 2.7배 |
| 데이터 분석 | 6 | **113** | **18.8배** |
| 학생 웹 프로젝트 | 5 | 17 | 3.4배 |
| Django | 5 | 23 | 4.6배 |

**(4) 실제 프로젝트에서 라이선스의 23.3%가 「추정」이다.**

실제 프로젝트 144개 패키지의 라이선스를 어느 경로로 얻었는지 세어보면 이렇다.

| 경로 | 비율 | 정확도 |
|---|---:|---|
| `license_expression` | 42.8% | 확실 |
| `license` 필드 정확 일치 | 27.2% | 확실 |
| **classifier** | **23.3%** | **추정 — 버전 구분 불가** |
| 별칭 사전 | 6.7% | 확실 |

classifier는 `Apache Software License`가 1.1인지 2.0인지, `BSD License`가 2-Clause인지 3-Clause인지 구분하지 못한다. **실제 프로젝트에서는 넷 중 하나가 이런 추정값이다.** 800개 표본의 10%보다 두 배 이상 높다.

이것이 이 도구에 대해 **가장 확실하게 측정된 사실**이다. 충돌보다도, 미상보다도.

## 0.3 권고 — 가치 제안 조정

| | 기존 (발표) | 수정 제안 |
|---|---|---|
| 한 줄 설명 | 라이선스 **충돌**을 잡아내는 도구 | 실제로 들어온 패키지 전부의 **현황판** |
| 1순위 | 충돌 판정 | **취약점** (가장 흔함) |
| 2순위 | — | **공개조건 + 미상** (4.33% + 3.37%) |
| 3순위 | — | 충돌 판정 (드물지만 걸리면 치명적) |
| 함께 표시 | — | **각 결과의 신뢰 수준** (23.3%가 추정값) |

충돌 판정을 **버리라는 것이 아니다.** 실재하고, 걸렸을 때의 비용이 크다(프로젝트 전체 공개). 다만 그것 하나만으로 도구를 정당화할 수 없다.

> **발표에서 든 `mysqlclient` 예시는 유효하다.** 실측에서 GPL-2.0-or-later로 확인됐다.
> **`jsonschema[format]` → `rfc3987`(GPLv3+)은 더 좋은 예시다.** 직접 설치한 것이 아니라 정말로 딸려오는 경우이고, 커뮤니티가 `format-nongpl` 대안을 따로 만들어 둘 만큼 알려진 문제다. 발표에서 이걸 쓰는 편이 낫다.

## 2.1 데이터 소스 — 세 곳 모두 사용 가능

### SPDX 라이선스 목록

```
GET https://raw.githubusercontent.com/spdx/license-list-data/main/json/licenses.json
HTTP 200   339,359 bytes   0.43초
```

| 항목 | 값 |
|---|---|
| 버전 | 3.29.0 |
| 릴리스 | 2026-09-16 (2주 전 — 활발히 관리됨) |
| 총 라이선스 | **740종** |
| OSI 승인 | 154종 (20.8%) |

| deprecated | 32종 |
| 예외(exceptions) | 86종 |

> **정정 사항.** 발표 준비 단계 체크리스트에 "SPDX의 OSI·FSF 플래그로 호환성 매트릭스 절반이 자동으로 채워진다"고 적었는데, 실측하니 OSI 승인은 740종 중 154종(20.8%)뿐이다. **플래그만으로는 5분의 1도 못 채운다.** 등급 분류는 수작업이 필요하다.

### PyPI JSON API

```
GET https://pypi.org/pypi/{name}/json
```

| 측정 | 값 |
|---|---|
| 800건 수집 (동시 10) | 5.9초, 실패 0건 |
| 3,000건 수집 (동시 12) | 17초, 실패 0건 |
| 응답시간 중앙값 | 34ms |
| p95 | 280ms |
| 최대 | 1,466ms |
| 인증 | 불필요 |

동시 12까지 rate limit에 걸리지 않았다. 다만 공식 문서에 명시된 한도가 없으므로 **동시 요청은 10 이하로 제한하고 User-Agent에 연락처를 넣는 것**을 설계 제약으로 둔다.

### OSV API

```
POST https://api.osv.dev/v1/querybatch
GET  https://api.osv.dev/v1/vulns/{id}
```

| 배치 크기 | 응답시간 |
|---:|---:|
| 50건 | 206ms |
| 200건 | 397ms |
| 500건 | **695ms** |

> 서로 다른 실제 패키지·버전으로 측정한 값이다. 같은 질의를 반복하면 1,849ms까지 늘어나므로, 초기 측정에서 이 함정에 빠졌다가 바로잡았다.

**설계상 중요한 제약:** `querybatch`는 취약점 **ID만** 돌려준다. 심각도(CVSS)를 얻으려면 ID마다 `GET /v1/vulns/{id}`를 따로 호출해야 한다. 228건 조회에 동시 12로 3.4초가 걸렸다. **심각도 표시를 요구사항에 넣는다면 캐시가 필수다.**

## 2.2 라이선스 식별 — 3단계 폴백이 필요하고, 충분하다

### 어느 단계에서 식별되는가 (800개 표본)

| 단계 | 상위 400 | 무작위 400 | 전체 |
|---|---:|---:|---:|
| 1. `license_expression` (PEP 639) | 44% | 27% | **35%** |
| 2a. `license` 필드가 SPDX ID와 정확 일치 | 28% | 28% | 28% |
| 2b. `license` 필드에 전문이 통째로 | 4% | 4% | 4% |
| 2c. `license` 필드가 자유 문자열 | 16% | 24% | 20% |
| 3. classifier | 8% | 11% | 10% |
| 4. 미상 | 1% | 7% | 4% |

### 누적 식별률 — 두 가지 정의를 구분해야 한다

측정 중 정의가 흔들리는 것을 발견했다. **"라이선스 표기가 존재하는 비율"과 "그것을 SPDX 식별자로 변환하는 데 성공한 비율"은 다르다.** 도구가 실제로 쓸 수 있는 것은 후자다.

| 정의 | 800개 표본 | 3,000개 표본 |
|---|---:|---:|
| ① 표기가 어디엔가 존재 | 96.2% | — |
| ② **SPDX 식별자로 변환 성공** | **93.9%** | **93.7%** |
| 차이 (표기는 있으나 변환 실패) | 2.38% | — |

**두 표본의 ②가 93.9%와 93.7%로 거의 일치한다.** 표본을 4배 늘려도 값이 유지되므로 신뢰할 만한 수치다.

단계별 누적(정의 ① 기준, 800개 표본):

```
              1단계만    +2단계    +3단계    표기없음
상위 400       43.8%    91.5%    99.2%     0.8%
무작위 400      26.8%    82.0%    93.2%     6.8%
전체           35.2%    86.8%    96.2%     3.8%
```

**해석 네 가지.**

1. **`license_expression` 하나만 보면 3분의 1밖에 못 읽는다.** PEP 639이 확산 중이지만 아직 소수다. 폴백은 선택이 아니라 필수다.
2. **2단계가 절반을 담당한다.** 여기가 가장 지저분하고, 가장 많은 작업이 몰린다.
3. **3단계(classifier)가 마지막 10%를 메운다.** 다만 대가가 있다 — 아래 참조.
4. **변환 실패 2.38%는 회수 가능하다.** 원인이 전부 사전 부족이나 전처리 미흡이다 (다음 항목).

### 변환 실패 2.38%의 정체 — 전부 고칠 수 있다

19건 전수를 확인했다.

| 원문 | 실패 이유 | 해결 |
|---|---|---|
| `GPLv2` | 별칭 사전에 없음 | 사전 추가 |
| `EPL` | 별칭 사전에 없음 | 사전 추가 |
| `MPL` | 별칭 사전에 없음 (버전 모호) | 사전 추가 + 추정 표시 |
| `GNU LGPL 2.1` | 별칭 사전에 없음 | 사전 추가 |
| `PSF license` | 후행 `license` 미제거 | 전처리 |
| `Apache Software License v2` | 별칭 사전에 없음 | 사전 추가 |
| `BSD 3-clause` | 대소문자 (`Clause` vs `clause`) | 소문자 정규화 |
| `3-clause BSD <https://...>` | URL이 붙어 있음 | 전처리 |
| `MIT License\n\n Copyright...` | 줄바꿈 뒤에 전문 | 첫 줄만 사용 |
| **`BSD 3-Clause OR Apache-2.0`** | **토큰화 실패** | **아래 참조** |

**마지막 사례가 설계상 중요하다.** `uritemplate`의 라이선스는 `BSD 3-Clause OR Apache-2.0`인데, 공백을 포함한 `BSD 3-Clause`가 SPDX 식별자가 아니어서 표현식 파서가 토큰을 쪼개다 실패한다.

→ **요구사항으로 반영:** 표현식을 파싱할 때 **각 토큰에 별칭 매핑을 먼저 적용**해야 한다. 그리고 자유 문자열 안의 복합 표기는 공백을 포함한 라이선스 이름을 다뤄야 하므로 토큰화가 표준 표현식보다 어렵다.

### 도달 가능한 식별률

| 경로 | 3,000개 표본 기준 |
|---|---:|
| 현재 (3단계, 사전 60종) | 93.7% |
| + 사전 보강·전처리 (실패 19건 유형 해소) | **약 96.1%** |
| + PEP 658 4단계 (§2.4) | **약 97.4%** |
| 나머지 (진짜 표기 없음, 대부분 NVIDIA 독점) | 2.6% |

**요구사항 목표는 95%로 잡는다.** 근거 있는 수치이면서 달성 가능하다.

### 2b의 함정 — 길이로 걸러야 한다

`license` 필드에 라이선스 **전문**을 통째로 넣은 패키지가 4%다.

```
matplotlib   74,646자
pandas       61,643자
scipy        55,271자
```

`if len(license) > 200` 같은 길이 조건이 없으면 사전 조회가 통째로 무너진다.

### 3단계의 대가 — classifier는 버전을 구분하지 못한다

classifier에 등장한 표기는 25종뿐이라 다루기 쉽다. 그러나 정밀도가 낮다.

| classifier | 빈도 | 문제 |
|---|---:|---|
| `Apache Software License` | 139회 | **1.1인지 2.0인지 모른다** |
| `BSD License` | 80회 | **2-Clause인지 3-Clause인지 모른다** |
| `MIT License` | 183회 | 문제 없음 |
| `GNU Library or Lesser GPL (LGPL)` | 5회 | **2.1인지 3.0인지 모른다** |

→ **요구사항으로 반영:** classifier에서 얻은 결과는 「추정」으로 표시하고, 버전 모호성을 사용자에게 알려야 한다. 등급 판정에는 **보수적으로 가장 강한 쪽**을 가정한다.

### 표기 변형은 사전으로 덮을 수 있다

`license` 필드에 등장한 서로 다른 문자열: **82종** (800개 표본 기준)
그중 SPDX ID와 정확히 일치: 13종 (16%)
**사전 매핑이 필요한 나머지: 69종**

빈도 상위를 보면 롱테일이 아니다.

```

O   63회  Apache-2.0

O   21회  BSD-3-Clause
X   15회  BSD
X   14회  MIT License
X    8회  Apache License 2.0
X    5회  Apache License, Version 2.0
X    5회  Apache Software License
X    4회  Apache-2.0 license
```

**상위 10종이 전체의 대부분을 덮는다.** 사전 60~80줄이면 현실적으로 충분하다. 다만 소문자 정규화, 공백 정리, 후행 "license" 제거 같은 전처리가 선행되어야 한다.

> **정정 사항.** 발표에서 "517개 조사, 46가지 표기"라고 말했다. 표본을 800개로 늘리니 82종이 됐다. 표본이 커지면 롱테일이 늘어나는 정상적 현상이지만, **발표의 숫자는 표본 크기와 함께 말해야 정확하다.**

## 2.3 SPDX 표현식 파서 — 범위가 명확히 한정된다

상위 3,000개 중 복합 표현식 빈도:

| 구문 | 건수 | 비율 |
|---|---:|---:|
| 단일 식별자 | — | **95.7%** (800개 표본 기준) |
| `OR` | 32 | 1.07% |
| `AND` | 18 | 0.60% |
| 괄호 | 2 | 0.07% |
| `WITH` | 2 | 0.07% |
| `+` 접미사 | 0 | 0.00% |

**괄호가 들어간 것은 3,000개 중 둘뿐이다.**

```
orjson        MPL-2.0 AND (Apache-2.0 OR MIT)
marisa-trie   MIT AND (BSD-2-Clause OR LGPL-2.1-or-later)
```

두 번째가 더 중요하다. **OR 선택지에 LGPL이 들어 있어 「OR = 가장 약한 것」 규칙이 실제로 판정을 좌우하는 유일한 괄호 사례**다.

전체 복합 표현식 목록(800개 표본):

```
Apache-2.0 AND Apache-2.0 WITH LLVM-exception AND BSD-2-Clause AND BSD-3-Clause AND BSL-1.0 AND MIT
Apache-2.0 AND BSD-2-Clause
Apache-2.0 AND CNRI-Python
Apache-2.0 OR BSD-2-Clause
Apache-2.0 OR BSD-3-Clause
Apache-2.0 OR GPL-2.0-or-later
BSD-3-Clause AND 0BSD AND MIT AND Zlib AND CC0-1.0
MIT AND BSD-3-Clause AND BSD-2-Clause
MIT AND PSF-2.0
MIT OR Apache-2.0
MPL-2.0 AND (Apache-2.0 OR MIT)
```

**함의:** 재귀 하강 파서 80~120줄이면 전수 커버된다. 외부 라이브러리(`license-expression`) 없이 직접 구현해도 되고, 그 편이 **수업 과제로서의 가치도 크다.** 실제 구현 시 주의할 곳은 우선순위 하나다.

```
+  >  WITH  >  AND  >  OR
```

그리고 등급 판정 규칙:

```
OR  = 여러 선택지 → 가장 약한 것을 고른다  (min)
AND = 모두 적용   → 가장 강한 것을 따른다  (max)
```

발표 때 "아직 못 고침"으로 소개한 `OR`를 `AND`처럼 다루는 버그가 여기서 발생한다. OR 32건 중 **선택지의 등급이 실제로 다른 것은 15건(0.50%)**이다. 나머지 17건(`packaging`의 `Apache-2.0 OR BSD-2-Clause`, `cryptography`의 `Apache-2.0 OR BSD-3-Clause` 등)은 양쪽 모두 허용형이라 OR를 AND로 처리해도 판정이 같다.

실제로 영향을 받는 것은 `dulwich`(`Apache-2.0 OR GPL-2.0-or-later`), `marisa-trie`, `pyside6`, `pycurl`, `paho-mqtt` 같은 경우다. **이쪽은 GPL이 걸려 있어 틀리면 멀쩡한 패키지를 「안 됨」으로 막는다.**

## 2.4 미상 구제 — PEP 658로 21% 회수 가능

미상 188건을 조사하다가 **PyPI JSON API의 `info`에는 라이선스가 없는데 wheel 내부 `METADATA`에는 있는 경우**를 발견했다.

```
mypy-extensions   info.license = null   →   wheel METADATA: License: MIT
azure-core        info.license = null   →   wheel METADATA: License: MIT
azure-identity    info.license = null   →   wheel METADATA: License: MIT
tiktoken          info.license = null   →   wheel METADATA: License: MIT License
uritemplate       info.license = null   →   wheel METADATA: License: BSD 3-Clause OR Apache-2.0
```

wheel 전체를 내려받는 것은 비싸다. NVIDIA 패키지는 실제로 수백 MB다 — `nvidia-cudnn-cu12` 772MB, `nvidia-cublas-cu12` 575MB. **PEP 658이 이 문제를 해결한다.**

```
GET {wheel_url}.metadata
```

| 패키지 | wheel 크기 | .metadata 크기 | 응답시간 |
|---|---:|---:|---:|
| nvidia-cuda-runtime-cu12 | 3.5 MB | **1.7 KB** | 17ms |
| tiktoken | 1.1 MB | 6.5 KB | 16ms |
| mistralai | 1.4 MB | 78.8 KB | 16ms |
| mypy-extensions | 0.005 MB | 1.1 KB | 67ms |

**미상 188건 전체에 적용한 결과: 40건 구제 (21.3%), 소요 3초.**

```
미상 비율  6.27%  →  4.93%      (식별률 93.7%  →  95.1%)
```

21%는 만족스럽지 않지만, 구제된 것이 `mypy-extensions`(129위), `azure-core`(173위)처럼 **실제로 많이 쓰이는 상위권**이라는 점에서 체감 효과는 더 크다.

나머지 148건의 상당수는 NVIDIA CUDA 패키지처럼 **실제로 독점 라이선스**이거나(`LicenseRef-NVIDIA-Proprietary`), 메타데이터에 정말 아무것도 없는 경우다. 후자는 「미상」으로 경고하는 것이 올바른 동작이다.

## 2.5 의존성 해석 — pip과 91~100% 일치

`requires_dist`를 재귀적으로 따라가는 방식으로 자체 해석기를 만들고, `pip install --dry-run --ignore-installed --report`의 실제 결과와 대조했다.

| 표본 | pip | 자체 | 일치 | 재현율 | pip 소요 | 자체 소요 |
|---|---:|---:|---:|---:|---:|---:|
| 웹앱 구성 | 30 | 30 | 30 | **100%** | 4.9초 | 1.0초 |
| 데이터 분석 | 113 | 103 | 103 | **91%** | 19.5초 | 2.0초 |
| 학생 웹 프로젝트 | 17 | 17 | 17 | **100%** | 2.7초 | 0.1초 |
| Django | 23 | 23 | 23 | **100%** | 3.2초 | 0.3초 |
| boto3 단독 | 7 | 7 | 7 | **100%** | 2.7초 | 0.1초 |

**놓친 10건의 정체는 전부 extras다.**

```
arrow, fqdn, isoduration, jsonpointer, lark, rfc3987-syntax,

```

`jsonschema[format-nongpl]`처럼 대괄호로 요청된 선택적 의존성 그룹을 처리하지 않아서 생겼다. 예측 가능한 실패이지만 **국소적이지 않다** — §3.2에서 보듯 이 경로가 GPL 유입의 주된 통로다.

### 환경 마커 처리량이 생각보다 크다

해석 중 마커 때문에 제외한 의존성 수:

| 표본 | 제외 건수 |
|---|---:|
| 웹앱 구성 | 127 |
| 데이터 분석 | **762** |
| Django | 105 |

다만 이 762건의 **98%는 `extra` 마커**이고 진짜 환경 마커는 19건이다(§3.2). 환경 마커 처리 자체는 두 자릿수 규모다.

`python_version`, `sys_platform`, `extra` 같은 조건을 평가해야 한다. `packaging` 라이브러리의 `Marker.evaluate()`가 이 일을 해주므로 직접 구현할 필요는 없지만, **환경 변수를 무엇으로 고정할지는 설계 결정 사항**이다.

### 근본적 한계 — 버전을 확정하지 못한다

메타데이터를 훑는 방식은 **각 패키지의 최신 버전**을 가정한다. pip은 버전 제약을 풀어 실제 설치 버전을 확정한다.

```
pip 결과:  boto3==1.43.105, botocore==1.43.105, urllib3==2.8.0, six==1.17.0
```

라이선스 판정에는 큰 영향이 없다(라이선스는 버전별로 잘 안 바뀐다). 그러나 **취약점 조회는 버전이 틀리면 결과가 통째로 틀린다.**

→ **설계 결정:** 두 가지 입력 모드를 제공한다.

| 모드 | 입력 | 속도 | 취약점 정확도 |
|---|---|---|---|
| 빠른 분석 | `requirements.txt` | 1~2초 | 낮음 (최신 가정) |
| 정확 분석 | `pip freeze` 결과 또는 lock 파일 | 즉시 | 높음 (버전 확정) |

이 두 모드가 **전략 패턴이 들어갈 자연스러운 자리**다. 수업 4주차 내용과 직결된다.

# 3. 제품 타당성 — 이 도구가 실제로 쓸모가 있는가

여기가 이 리포트에서 가장 중요한 절이고, **측정을 두 번 한 절**이다.

## 3.1 1차 측정 — 충돌 0건

실제 프로젝트 5종(고유 144개 패키지)에 MIT 기준으로 판정을 돌렸다.

| 표본 | 총계 | 써도 됨 | 조건 있음 | **안 됨** | 모름 | 보류 |
|---|---:|---:|---:|---:|---:|---:|
| 웹앱 구성 | 30 | 29 | 1 | **0** | 0 | 0 |
| 데이터 분석 | 103 | 100 | 1 | **0** | 0 | 2 |
| 학생 웹 프로젝트 | 17 | 16 | 1 | **0** | 0 | 0 |
| Django | 23 | 22 | 1 | **0** | 0 | 0 |
| boto3 | 7 | 7 | 0 | **0** | 0 | 0 |

「써도 됨」이 아닌 전체 목록:

```
조건 있음   certifi           MPL-2.0              (웹앱·데이터분석·학생웹 3개 표본)
조건 있음   psycopg2-binary   LGPL-2.1-or-later    (Django 표본)
판단보류    cffi              MIT-0                (SPDX ID지만 등급표에 없음)
판단보류    pillow            MIT-CMU              (동일)
```

여기까지 보고 "충돌 탐지라는 전제가 약하다"고 결론냈다. **틀렸다.**

## 3.2 2차 검증 — 왜 0건이 나왔는가

### 결함 1. `extras`를 통째로 건너뛰었다

해석기가 `extra == "..."` 마커가 붙은 의존성을 전부 버리도록 짜여 있었다. §2.5에서 "환경 마커 762건"이라고 보고한 것을 분해하면 이렇다.

| 표본 | 제외 합계 | **`extra` 마커** | 진짜 환경 마커 |
|---|---:|---:|---:|
| 데이터 분석 | 762 | **743 (98%)** | 19 |
| 웹앱 | 127 | 122 (96%) | 5 |
| 학생 웹 | 71 | (미분해) | — |
| Django | 105 | 100 (95%) | 5 |
| boto3 | 8 | (미분해) | — |

**extras 경로로 들어오는 의존성은 측정될 수 없었다.** 「안 됨 0건」은 발견이 아니라 설계상 보장된 결과다.

### 반례가 표본 안에 있었다

데이터 분석 표본의 `jsonschema`를 직접 확인했다.

```
jsonschema[format]
   → fqdn, idna, isoduration, jsonpointer, rfc3339-validator,
     rfc3987, uri-template, webcolors
                ↑
     rfc3987   license: "GNU GPLv3+"
               classifier: "GNU General Public License v3 or later (GPLv3+)"

jsonschema[format-nongpl]
   → 같은 목록에서 rfc3987 대신 rfc3986-validator + rfc3987-syntax (MIT)
```

**`format-nongpl`이라는 extra가 존재한다는 사실 자체가 증거다.** 파이썬 커뮤니티가 "GPL이 딸려오는 문제"를 실재하는 것으로 다루고, 그것을 피할 대안을 따로 만들어 두었다는 뜻이다.

파이썬 생태계에서 가장 잘 알려진 사례를 1차 측정은 정반대 근거로 쓸 뻔했다.

### 결함 2. 「미상」 통에 공개조건이 숨어 있었다

미상 188건을 분해했다.

```
정말 아무 표기도 없음      101건  3.37%
표기는 있으나 변환 실패     87건  2.90%   ← 우리 해석기의 실패
```

| 패키지 | 표기 | 성격 |

| 항목 | 1차 | 2차 |
|---|---:|---:|
| 약한 공개조건 | 2.47% | 2.47% |
| 강한 공개조건 | 1.03% | 1.03% |

여전히 소수지만, **1차 측정이 이것을 0으로 보이게 만들었다는 점이 중요하다.**

## 3.3 그래서 위협 모델은 유효한가

| | 발표에서 말한 것 | 1차 측정 결론 | **2차 검증 결론** |
|---|---|---|---|
| GPL이 몰래 딸려오는가 | 그렇다 | 아니다 | **그렇다. 주로 extras 경로로** |
| 얼마나 흔한가 | (암시: 흔함) | 1.03% | **4.33%, 단 대부분은 도구** |
| 탐지하기 쉬운가 | — | 직접 의존성만 봐도 됨 | **extras와 비표준 표기를 다뤄야 함** |
| 도구가 필요한가 | 그렇다 | 약함 | **그렇다. 사람이 손으로는 못 한다** |

**발표의 전제는 대체로 유효했다.** 1차 측정이 그것을 부정한 것은 측정 결함 때문이었다.

다만 **설명은 바뀌어야 한다.**

- "GPL이 전이 의존성으로 끌려온다" → 맞지만, 주된 경로는 **extras**다
- "43개 중에서 찾아내는 게 일이다" → 맞다. 그리고 **표기가 제각각이라 기계도 놓친다**는 것이 더 정확하다

## 3.4 그러나 취약점이 훨씬 흔하다

공개조건이 실재한다고 해서 그것이 **제품의 1순위**가 되는 것은 아니다.

같은 패키지 15개, 버전만 바꿔 OSV에 조회한 결과다.

```
2021년경 고정   ████████████████████████████████████████  228건  (12/15 패키지)
2024년말 고정   ███████████████████████                   130건  (10/15 패키지)
오늘 최신       (0건)                                        0건  ( 0/15 패키지)
```

심각도 분포(228건 중):

| 구간 | 건수 | 비율 |
|---|---:|---:|
| 높음 (원격 공격 + 영향 큼) | 101 | 44.3% |
| 그 외 | 82 | 36.0% |
| 심각도 정보 없음 | 45 | 19.7% |

**함의 두 가지.**

- 학생 프로젝트는 `requirements.txt`를 고정해두고 갱신하지 않는다. 학기 초 0건이 다음 학기 재사용 시점에는 수백 건이 된다. **공개조건보다 두 자릿수 이상 자주 발생한다.**
- 228건을 그대로 나열하면 읽히지 않는다. **심각도 필터가 편의 기능이 아니라 기능 요구사항이다.**

## 3.5 가장 잘 측정된 사실 — 넷 중 하나는 추정값

실제 프로젝트 144개 패키지의 라이선스를 어느 경로로 얻었는지 세면 이렇다.

| 경로 | 비율 | 신뢰 |
|---|---:|---|
| `license_expression` | 42.8% | 확실 |
| `license` 필드 | 27.2% | 확실 |
| **classifier** | **23.3%** | **추정 — 버전 구분 불가** |
| 별칭 사전 | 6.7% | 확실 |
| 미상 | 0% | — |

classifier는 `Apache Software License`가 1.1인지 2.0인지, `BSD License`가 2-Clause인지 3-Clause인지 말해주지 않는다. **실제 프로젝트에서는 라이선스 넷 중 하나가 이런 추정값이다.** 800개 표본의 10%보다 두 배 이상 높다.

이것이 이 도구에 대해 **가장 확실하게 측정된 사실**이다. 충돌보다도, 미상보다도.

→ **요구사항으로 반영:** 모든 결과에 신뢰 수준을 함께 표시한다(FR-L-06, FR-J-12).

## 3.6 수정된 한 줄 설명

> `requirements.txt`를 올리면 실제로 설치되는 패키지 전부를 펼쳐서,
> **알려진 취약점** · **공개 조건이 붙은 것** · **라이선스를 알 수 없는 것**을
> 한 화면에 보여주는 웹앱. 각 결과가 얼마나 확실한지도 함께 표시한다.

## 5.1 모듈 독립성

다섯 모듈이 주고받는 것은 목록 하나뿐이다.

# 7. 법적·윤리적 검토

## 7.1 도구가 법률 조언을 하는가

**한다고 오해될 수 있다.** 완화책 세 가지를 요구사항에 넣는다.

1. **모든 결과 화면에 고정 문구.** "본 결과는 법적 조언이 아니며, 배포 전 전문가 확인이 필요합니다."
2. **「조건 있음」을 「안 됨」과 분리.** 약한 공개조건은 사용 형태에 따라 달라지므로 단정하지 않고 확인 항목만 제시한다.
3. **판정 근거를 항상 함께 표시.** "GPL-3.0(강한 공개조건) > MIT(허용형)" 형태로, 사용자가 스스로 검증할 수 있게 한다.

## 7.2 오판정의 방향

| 오류 유형 | 결과 | 허용 여부 |
|---|---|---|
| 위험한 것을 「써도 됨」으로 (미탐) | 사용자가 법적 위험을 모른 채 배포 | **가장 나쁨** |
| 안전한 것을 「안 됨」으로 (오탐) | 사용자가 멀쩡한 패키지를 뺌 | 불편하지만 안전 |

→ **설계 원칙: 불확실하면 보수적으로.** classifier 추정, 등급 미등록, 미상은 모두 「확인 필요」 쪽으로 보낸다. 다만 `OR` 표현식만은 예외로 **가장 약한 선택지**를 취한다. 사용자에게 선택권이 실제로 있기 때문이다.

## 7.3 외부 API 이용

| API | 조건 | 준수 방안 |
|---|---|---|
| PyPI | 명시적 한도 없음. Fair use 요구 | 동시 10 이하, User-Agent에 연락처, 24시간 캐시 |
| OSV | 무료, Apache-2.0 데이터 | 배치 사용, 결과 캐시 |
| SPDX | 저장소에 LICENSE 파일 없음 (확인 필요) | 출처 표기. 사용 전 SPDX 측에 확인할 것 |

**캐시는 예의 문제이자 성능 문제다.** 여러 사용자가 같은 패키지를 조회하므로 적중률이 높다.

## 7.4 우리 도구 자신의 라이선스

**이 도구는 자기 자신을 검사할 수 있어야 한다.** 좋은 데모이자 자기 검증이다. MIT로 공개하고, 우리가 쓰는 의존성이 전부 허용형인지 스스로 확인한 결과를 README에 넣는다.

# 11. 결론

## 11.1 답

**만들 수 있다.** 기술적 장애물은 실측으로 모두 해소됐다.

- 데이터 3종 전부 무인증·무료·안정적 (실패율 0%)
- 라이선스 식별 93.7%, 사전 보강·PEP 658 추가 시 97.4%까지 도달 가능
- 의존성 해석이 pip과 91~100% 일치
- 취약점 조회 500건 0.7초 (서로 다른 실제 패키지 기준)
- 복합 표현식 파서 범위가 120줄 이내로 한정됨

**완성할 수 있다.** 다만 여유는 없다.

- 240시간 가용 대 250시간 필요 → §6.3 제외 항목을 반드시 지킨다
- 모듈 5개가 독립적이라 병렬 개발 가능
- 각 역할에 축소판이 있어 1명이 막혀도 전체가 멈추지 않는다

## 11.2 조건

**발표에서 말한 「충돌 탐지 도구」라는 전제는 유효하다.** 1차 측정이 그것을 부정했으나, 교차 검증에서 그 부정이 측정 결함에서 나온 것임을 확인했다(§3.2).

다만 가치 제안의 순서는 조정해야 한다.

> 내 프로젝트에 실제로 들어온 패키지를 전부 펼쳐서,
> **취약점**(가장 흔함) · **공개 조건**(4.33%) · **표기 없음**(3.37%)을
> 한 화면에 보여주는 웹앱.
> **각 결과가 얼마나 확실한지도 함께 표시한다**(실제 프로젝트에서 23.3%가 추정값).

이 변경은 **구현 범위를 거의 바꾸지 않는다.** 만들 것은 같고, 화면의 무게 중심과 설명이 달라진다.

**다만 요구사항 두 개가 「권장」에서 「필수」로 올라간다.**

| 요구사항 | 이유 |
|---|---|
| FR-C-09 extras 처리 | 이것 없이는 GPL 유입 경로를 못 본다 (§3.2) |
| FR-L-09/13 사전 보강·정규화 | 이것 없이는 공개조건 24건을 미상으로 묻는다 (§3.2) |

## 11.3 팀원에게 먼저 말할 것

9/28에 배정된 팀원들에게 첫 모임에서 이 리포트의 §3을 공유하기를 권한다.

- 팀장이 전제를 스스로 검증했고, **틀린 부분을 먼저 밝혔다**는 사실이 신뢰를 만든다
- 「등급표 작성」과 「판정 로직」이 비어 있음을 보여주면 각자 맡을 것이 분명해진다
- 숫자가 있으면 "이거 되는 건가요"라는 불안이 줄어든다
